# 阵营卡片Hover重复播放修复

日期：2026-10-15。仅修复按钮Hover边界；不创建整理阶段，不修改视觉/布局/动画、音频素材、地图或玩法，不暂存/提交/推送。

## 根因及实际复现

`ThreeGame` 在容器上只注册一个 `pointerover` 委托监听。该事件在数字、标题、图片、说明和箭头等子元素间切换时也会冒泡。旧 `onAudioHover` 只检查 `target.closest('button')`，没有检查 `relatedTarget` 是否仍在同一按钮内，导致每次子元素切换都调用播放。

明确打开 `http://127.0.0.1:5173/` 并核对标题后，Chrome原生鼠标在同一DeepSeek卡数字→标题→说明→数字间移动，得到4次播放调用和4个真实AudioBufferSourceNode.start。后三个事件的relatedTarget均在原卡片内，卡片DOM引用不变。排除重复监听、DOM重新挂载；箭头是同一按钮内的span，没有独立Hover入口。见 [修复前调用/事件记录](ui-hover/before.json)。

## 最小修复

只修改 `src/three/ThreeGame.ts` 的 `onAudioHover`：找到目标按钮，若 `relatedTarget` 是Node且被同一按钮包含，则直接返回；否则按原音量/总线播放。保留原委托监听及销毁注销，不增加状态、计时器或监听，不改90ms冷却/并发限制。整张阵营卡原本就是原生button，因此它自然成为唯一Hover边界；真正离开后重新进入无需手工重置状态。其他按钮遵守相同原生边界语义，点击逻辑未改。

新增 `tests/ui-hover-boundary.test.mjs`，用Node原生类型擦除与VM执行从真实源码提取的处理器，不复制修复逻辑、不启动WebGL。覆盖100次卡内子元素切换、卡片自身、离开重进、两卡切换、null/非Node来源与非按钮区域。录音播放替身没有冷却，确保不是靠节流掩盖问题。修复前3项中2失败/1通过，修复后3/3通过。

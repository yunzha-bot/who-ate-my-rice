# 区域级放大复核材料（2026-10-04）

本目录是**本轮「Gameplay 住宅区域级放大 + 外围建筑 parcel 约束」的证据**。它不是游戏源码的一部分，不参与玩法、碰撞或导航；`view.html` 与 `plan.html` 只被 Vite 开发服务器当作静态页面读取（`http://127.0.0.1:5173/docs/verification/MAP_SCALE_UP/...`）。

## 1. 本轮做了什么

上一轮的扩建是**加房间**（12 → 18 个空间）。用户指出方向偏差：要的是**保持区域结构与功能关系，把整个 Gameplay 住宅的空间尺度放大**——房间更宽、走廊更宽、家具间距与门距更大、追逐更舒展，而**不是**继续堆小房间。

本轮据此重排整张平面：

- **房间数、房间连接关系、31 扇门的配对、6 条环路、东翼结构全部不变**。做法是把由 `ROOMS` 边界唯一化得到的旧网格线逐条映射到新网格线，每个房间仍由**同一组网格线下标区间**定义，所以拓扑是**构造上保证**不变，而不是「改了以后测试还没发现」。
- `MAP_WIDTH 48 → 56`、`MAP_DEPTH 30 → 38`；平面**重新以原点为中心**（旧图 X `-18…24` 中心是 `+3`，旧世界盒却是 `-24…24`，西侧多出 `x ∈ [-24,-18]` 一段被外墙封死的不可达余量，本轮收回）。
- 房间总面积 `1143 → 1950`（×1.71），各区域倍率区间 `1.47–1.87`。
- **家具一件都没有放大**（仍是同一套人物比例的白模），只补了 8 件普通家具（32 → 40）。
- 外围街区改为显式 **Parcel / Footprint 模型**，联排改为共享整段基座与分户墙，所有坐标改为从住宅 bbox 推导。

没有修改 `GAME_CONFIG`、AI 决策、S7D 判据、技能 CD、胜负条件或玩家声音可视化状态。

另有一个**一次性探针**（跑完即删，不在仓库里）直接 import 真实地图数据 + `CollisionWorld` + `NavigationSystem` + `DoorSystem`，逐项复核：

- 18 个房间互不重叠、`MAP_WIDTH` / `MAP_DEPTH` 与世界盒一致、去重后房间尺寸 ≥ 8 种；
- 31 扇门的墙洞宽度精确等于 `1.2`；门中心与两侧各 1 个角色直径的接近点都可站立（无家具、无墙）；
- 屏蔽任意单扇门后 18 个房间仍全部可达（2-边连通）；
- 每件家具完整落在所属房间内、不与墙或其它家具重叠、尺寸在编辑器白模合法范围内；
- 0.3 步长网格 BFS 覆盖全部 18 个房间内部、14 个米点、2 个参考出生点、31 扇门中心与 62 个接近点；
- 8 个藏身锚点逐项满足：房间内、可站立、离墙/家具 ≥ 0.05、离所属家具 0.05–0.9、离最近门段 ≥ 2.0、离最近米点 ≥ 1.2、`facing` 与 `atan2` 反算一致、有可用导航格心、从两个出生点 A* 可达。

结果：全部通过（`ALL CHECKS PASS`），地图规模 `56 × 38`、房间 18、门 31、家具 40、墙段 55（合并后的直墙段数；合并前 129 段）、房间总面积 `1950.00`。

### 顺带修掉的一个真实缺陷

新平面里 `door_hall_bathroom`（z=3.75）与 `door_dining_east_hall` 落在分带中段，使 `buildWalls()` 生成了一段 **0.15 长的墙垛**。`MapBuilder` 渲染墙时会按「短轴」放大 `HOME_COMPOSITION.wallThicknessScale`（1.8），而 0.15 < 墙厚 0.18，于是它放大的是**墙长**而不是墙厚，向门洞内溢出 0.06，门框立柱与墙穿模（`tests/door-visual-clearance.test.mjs` 直接报 `door_hall_bathroom frame jamb-left overlaps wall_015`）。修法是让 `buildWalls()` 在生成后**合并同一中心线上首尾相接的墙段**，从源头消除退化短垛；墙的实际位置没有任何改变，墙段总数 129 → 55。

## 4. 只读顾问 Codex 的审查结论（已记录，部分未采纳）

Codex 只读审查了本轮的放大方案与外围方案，**独立核算**确认：

- 新旧房间的 **36 组几何共享边关系完全相同**，31 门配对不变，没有任何共享边 ≤ 1.2，所有共享边都比旧图变长 → **放大没有破坏拓扑**；
- 未采纳项 ①：**三扇门可精简**（`balcony↔kitchen`、`storage↔dining` 为首选，`dining↔south_hall` 次选）。这属于拓扑修改，本轮 31 扇门全部保留，留给用户拍板；
- 未采纳项 ②：**`viewHeight` 14 → 15.0**（实际正交高度 14 × `playViewScale` 1.3 = 18.2）。相机可见范围会影响玩家决策，按「发现现有数值不适合先记录、不擅自调」的规则只做记录；
- 已采纳项：总面积倍率从 1.78 收到 1.71、各区域倍率去机械化（1.71–1.87 → 1.47–1.87）、外围改用 Parcel / 最小间距（`MIN_BUILDING_GAP = 4`）模型并新增跨建筑重叠检查。

## 5. 已知限制

- **本目录的截图来自 DPH 自己的浏览器复核，不是用户人工验收。** 相机视角由 `view.html` 指定，不代表真实对局中的跟随镜头手感。
- 整局种子扫描（`tests/s7d-full-match.test.mjs` 的同款逻辑仿真，非实机）发现 31 个种子里有 **3 个**（`20263151` / `20292603` / `20261234`，Human AI 主动抓捕、玩家挂机）在 150 秒帧数上限内不再结算，仍停在 `PLAYING`。这是**放大后路程变长、而所有平衡数值未改**的观测量，不是缺陷；是否需要 Balance Pass 由用户决定。
- **藏身判定变得比放大前更宽松（实测，值得单独评估）**：把 0.02 步长的格点扫过全部 8 个藏身交互区域（约 5 万个「可站立且在区域内」的点）后，**没有任何一点**会得到 `SURFACE_BLOCKED`（家具表面被墙挡住）或 `NOT_NAVIGABLE`（区域内没有可用导航格心）；全图扫描只在车库 `(27.0–27.4, 4.9)`（家政间|车库 隔墙与 `garage_workbench` 之间）与客房 `(27.1–27.4, -18.5)`（`guest_wardrobe` 与外墙之间）两处找到这类窄缝，而它们都不是藏身区域。原因是**房间放大约 1.7 倍而家具尺寸没变**，家具与墙之间不再形成放大前那种「站得住、却被墙隔在家具表面之外」的几何。放大前 `SURFACE_BLOCKED` / `NOT_NAVIGABLE` 是真实可达的拒绝码，现在只剩测试里人工搬动一件家具才能构造出来（`tests/hide-interaction-region.test.mjs` 与本轮复核都如实记录了这一点）。**这不是 bug，但会改变藏身玩法的实际难度**，需要用户人工跑图判断是否可接受。
- 外围街区的「连续感」与放大后的追逐手感**都需要用户人工跑图确认**；自动化只能保证几何不重叠、不压道路、连通与可达。

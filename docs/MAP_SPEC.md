# S5｜住宅平面图版 3D 灰盒地图（Gate = PASS）

本方案以用户提供的 `D:\桌面\偷大米小游戏\场景图.png` **左侧平面图**为位置基准，按追逐与镜头可读性放宽房间、门洞、走廊和家具间距。旧版等大房间 3×3 九宫格方案为 **Deprecated / 已废弃**。数据在 `src/three/map/apartmentMap.ts`；Three.js 几何与碰撞由 `src/three/map/MapBuilder.ts` 建立。X/Z 是地面，Y 是高度；下文坐标是游戏尺度，不是实际房屋测绘尺寸。

## 外轮廓与空间尺度

地图包围盒 `56 × 38` 世界单位（X `-28…28`，Z `-19…19`）。实际可走轮廓由不同大小的房间矩形拼接而成：北侧阳台突出，左侧卧室区与卫生间错位，右上厨房/储物间凸出，右下玄关伸出，最东侧是东翼；地图外空白不可通行。比例是基于参考图的游戏化放大，不能以真实住宅门宽直接推算；角色直径约 `0.533`，主走廊宽 `6.5`，两条长走廊与储物间宽 `4–4.5`，门洞宽 `1.2`。

> **2026-10-04 区域级放大（当前）**：整张平面按「区域」重排——房间数、房间连接关系、门的配对、环路、东翼全部不变，只是每个区域的可活动面积明显变大。做法是把由 `ROOMS` 边界唯一化得到的旧网格线，逐条映射到一组新的网格线，每个房间仍由**同一组网格线下标区间**定义，所以拓扑是**构造上保证**不变的。
>
> 这不是 uniform scale，也不是视觉 Mesh 缩放：主客厅 `12×15 → 16×20.5`、主卧 `9×10 → 12×14`，而附属空间（阳台、北阳台、衣帽间、卫生间、家政间）与走廊明显少放大。**家具一个都没有放大**，仍是同一套人物比例的白模，因此多出来的面积全部变成可活动空间。房间总面积 `1143 → 1950`（×1.71），住宅外接框 `42×30 → 56×38`。
>
> **世界盒仍必须关于原点对称**：`CollisionWorld` 与 `NavigationSystem` 只接受 `halfWidth / halfDepth`，没有中心偏移参数，所以 `MAP_WIDTH = 56` 一定对应 X `±28`。旧图 X `-18…24` 的中心是 `+3`，世界盒却是 `-24…24`，西侧因此多出 `x ∈ [-24,-18]` 一段被外墙封死的不可达余量；本轮把平面**重新以原点为中心**，这段浪费被收回。
>
> 深度取 `38` 而不是 `40`：只读顾问 Codex 审查后指出，各区域若一律 `×1.33` 就退化成「机械统一缩放」，且总面积倍率 `1.78` 已是固定移动 / 视野 / 感知数值下的上沿。于是只把两端**只服务附属空间与走廊端点**的分带各收 `0.5`，倍率区间从 `1.71–1.87` 拉成 `1.47–1.87`，主客厅 / 主卧 / 厨房 / 储物间仍保持上档。

## 房间连接与自然追逐环路

门洞/半开放连接由 `DOOR_NODES` 描述，每个节点有 ID、坐标、旋转、宽度和两侧 Room ID。当前始终开放，顶部橙色横梁只是调试占位，**没有门玩法**。共享墙面只有指定连接处开口，不是每面墙都开门。门前后用角色尺度检查，不把家具直接塞到门洞口。

**31 扇门（ID 与配对自东翼扩建起一个未改）**，门中心仍由 `makeDoor()` 取共享边中点，所以房间一放大，门与门的距离就自然拉开，门也不会贴墙角：门洞宽度恒为 `1.2`，放大后最窄的共享边是 `balcony↔kitchen` 与 `storage↔dining` 的 `2.5`，门叶两侧各留 `0.65` 墙垛；同一面墙上最近的两扇门是阳台东墙的 `balcony↔kitchen` 与 `balcony↔north_balcony`，中心距 `2.75`、门洞之间净墙段 `1.55`。其余同墙门对（探针实测中心距 / 门洞间净距）：主走廊西墙 `5.25 / 4.05`，玄关北墙 `7.25 / 6.05`，主卧东墙 `7.00 / 5.80`，厨房西墙 `6.75 / 5.55`，储物间西墙 `8.00 / 6.80`，餐厅东墙 `4.50 / 3.30`，餐厅南墙 `4.00 / 2.80`，客厅东墙 `10.25 / 9.05`，北阳台南墙 `6.00 / 4.80`，东走廊两侧 `9.25 / 8.05`。没有任何两扇门洞直接相邻。

> **门数精简建议（只读顾问 Codex 审查结论，本轮未采纳）**：Codex 独立核算确认「新旧房间的 **36 组几何共享边关系完全相同**、31 门配对不变、没有任何共享边 ≤1.2、所有共享边都比旧图变长」，即放大**没有破坏拓扑**。它同时给出三扇「可以删」的门作为建议，但明确说明这已经属于拓扑修改，不能由实现方自行采用：① `balcony↔kitchen`（共享边只 2.5，且与 `balcony↔north_balcony` 中心仅隔 3.25）；② `storage↔dining`（同样只有 2.5）；③ 次选 `dining↔south_hall`（与 `dining↔entry` 同墙中心距 4，但它是上一轮专门加的南走廊三向决策点，设计价值明显）。**本轮 31 扇门全部保留**，留给用户决定是否精简。

人工跑图的三条主环路：

1. **公共区**：客厅 → 餐厅 → 厨房 → 客厅。餐厅桌可在环内绕行。
2. **主卧区**：主走廊 → 主卧 → 衣帽间 → 主走廊。主卧床可从两侧绕开。
3. **卧室区**：主走廊 → 卫生间 → 次卧 → 书房 → 主走廊。书房另有通往玄关的次入口。

2026-10-03 东翼扩建又补出三条（共 6 条，`ROUTE_LOOPS`）——重点是让追逐有**绕行而不是加面积**：

4. **东南大环**：玄关 → 南走廊 → 东走廊 → 餐厅 → 玄关。它把玄关与餐厅之间原本的短连接改成一条可以绕的追逐路线；南走廊同时接玄关、餐厅与东走廊，是三向决策点而不是长管道。
5. **东翼环**：东走廊 → 家政间 → 客房 → 北阳台 → 储物间 → 东走廊。客房因此不是单出口尽头。
6. **北侧环**：客厅 → 厨房 → 北阳台 → 阳台 → 客厅。北阳台有三个出口，是有效的北侧绕行带。

此外阳台连接客厅与厨房，储物间连接厨房与餐厅，玄关连接书房、客厅和餐厅；**关闭连接图中任一单个 DoorNode 后其余 18 个区域仍可达**（2-边连通，无桥边）。上述“可达”由 `tests/apartment-map.test.mjs` 的自动空间检查与 S5 人工跑图验收共同确认；东翼部分是 2026-10-03 新增，待用户人工跑图验收。

东翼与老宅之间刻意保留**四个互相独立的接合点**，避免新空间只能从一条路进入：北阳台↔厨房/储物间、东走廊↔餐厅/储物间、南走廊↔玄关/餐厅、车库与家政间↔东走廊。每个新增空间至少两扇门。

## S7C-3｜每局出生与门初态（用户集中人工验收 8/8 通过）

上文 S5 的两个固定出生坐标和门常量是**地图参考值与历史规则**。S7C-3 运行时保留同一公寓、墙体、家具、房间、门 ID、米点和藏身点；只为每局选取双方实际出生格及 **31 扇门**（2026-10-03 东翼扩建前为 18 扇）的 `OPEN / CLOSED` 初态。出生候选从当前已应用地图的各房间真实空闲导航格产生，必须不同房间、相距至少 10 世界单位，且不能落在墙、家具、门叶或米堆交互范围内。每局用同一种子抽 5 份米，按真实碰撞与导航检验双方、米堆、所有 18 个房间和 8 个藏身锚点可达；普通 `CLOSED` 门可依照现有规则开启，初始不生成 `LOCKED`。20 次失败后使用经同样校验的全关门安全回退。**2026-10-04 区域级放大没有改变门数，也没有改变这条链路**；导航格数随世界盒从 `48×30` 增到 `56×38`（格数约 +48%），建图与 A* 仍是同一套实现。

> **扩建带来的已知兼容性变化**：门数增加会改变 `createMatchSetup()` 的随机数消耗顺序，因此**同一个 `matchSeed` 不再复现扩建前的布局**（固定种子仍然可复现扩建后的布局）。新增房间只要存在自由导航格就会自动进入每局出生候选池，`SPAWNS` 仍只作为参考点与安全回退。
>
> **2026-10-04 区域级放大没有改门数（仍 31）与房间数（仍 18）**，但世界盒与导航格变了，`MatchRandom.spawnCandidates()` 的候选列表随之改变，所以**同一个 `matchSeed` 同样不再复现东翼扩建轮的出生与门初态**（固定种子仍可复现本轮之后的布局）。这一点已由 `tests/s7d-full-match.test.mjs` 的整局种子扫描确认，详见 `docs/AGENT_LOG.md` 本轮条目。

开发地图标记中的 `DS REF SPAWN / HU REF SPAWN` 仅指原始参考出生点；本局实际出生、门状态、种子和校验结果在 DEV「本局随机布局」分类与 AI JSON 导出中查看。正常新局和重开产生新种子；DEV 固定种子可复现。场景热应用后，碰撞和导航仍由编辑器重建，下次新局按已应用地图重新生成候选；不导入或随机移动家具。
